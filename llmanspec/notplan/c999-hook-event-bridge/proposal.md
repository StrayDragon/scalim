## Why
当前 hook/event 主要面向进程内观察与回调,难以作为“触发器”连接外部系统或其他 `scalim` 实例,导致:
- 异步聚合/增量计算需要额外手工 glue code
- 无法在不阻塞主流程的前提下可靠投递事件

与此同时,事件目录与 hook 分发本身已经有相当成熟的仓库内基础: 事件类型、元数据与分发路径已存在,当前缺的不是“重新定义事件体系”,而是把既有事件流安全地桥接到进程外.

**核心示例(异步触发):**
- 详情输出产生订单事件 → 异步触发另一个 `scalim` 进行供应商利润率汇总

**类似示例:**
- 运行进度事件 → 发送到监控系统/通知系统
- Loader 性能事件 → 持久化到监控指标仓库
- 诊断告警事件 → 触发风控或数据质量检查
- 批次完成事件 → 触发下游缓存刷新或指标热更新
- 明细行事件 → 触发流式特征计算或实时画像更新

## What Changes
- 聚焦在“对外异步桥接”能力本身：将现有事件流包装为标准事件包,并支持非阻塞投递到外部传输层(例如队列/HTTP/文件).
- v1 仅要求最小可用桥接切片：显式启用/禁用、标准事件包、异步投递边界、以及对现有事件顺序/负载的影响说明.
- 在进入实现前,应先补一轮事件负载、顺序要求、失败模式与提交点语义的调研,再决定是否需要 outbox/backpressure/reliable mode 等增强能力；proposal 当前不预设这些结论.
- 事件目录、事件元数据与进程内分发语义继续复用现有 observability / event catalog 口径,本 change 只约束 bridge 如何消费并对外投递这些事件,不重复定义其 SSOT.

## Impact
- 受影响规范应主要聚焦在 `event-bridge` 能力本身；若涉及事件目录/元数据,应继续归属现有 hooks/observability 规范.
- 涉及组件: Hook 事件分发、可观测性事件包装、异步投递与失败策略.
- 主要风险: 事件负载过大、异步投递失败、背压影响主流程,以及并发执行模式下提交点回放带来的“顺序稳定但非实时”事件形态.
