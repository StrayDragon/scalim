## Context

基线扫描结果显示,当前 `src/scalim/` 非 vendor 代码中共有 `247` 处 `dynattr` 调用,主要集中在:

- `src/scalim/dsl/` 110 处
- `src/scalim/ob/` 46 处
- `src/scalim/execution/` 32 处
- `src/scalim/workflow/` 31 处

这些调用并不都属于同一性质:

- 一部分是 DSL / 反射式框架边界,确实需要动态属性访问.
- 一部分是对已知 dataclass / IR / 运行时对象字段的读取,理论上可以直接静态化.
- 还有一部分是为了兼容第三方对象结构差异而做的宽松访问,需要显式注释说明而不是隐式散落.

## Goals / Non-Goals

**Goals**
- 提供一个稳定、可重复运行的 `dynattr` 清点工具.
- 为“必须动态”的场景建立显式 allow 契约,避免隐式扩散.
- 为后续接入 `just qa` 提供可执行的收口顺序.

**Non-Goals**
- 本阶段不要求一次性消除全部 `247` 处调用.
- 本阶段不直接将新检查接入 `just qa`,避免在基线尚未分类前造成噪声门禁.

## Decisions

- **检查入口**: 使用独立脚本 `scripts/check-dynattr.py`,通过 `uv run` 执行.
- **扫描范围**: 默认扫描 `src/scalim/`,排除 `src/scalim/vendor/` 与构建/缓存目录.
- **命中规则**: 任何 `getattr` / `setattr` / `hasattr` 调用都视为命中,不区分属性名是否为字符串字面量.
- **例外机制**:
  - 行级 allow 适用于局部、确属必要的动态边界.
  - 文件级 allow 仅适用于整文件都以动态反射为主要职责的模块.
  - allow pragma 属于治理标记,在完成静态化替代前不得随意移除.
- **收口顺序**:
  - 先产出基线报告.
  - 再按目录/职责将命中分为“可重构静态化”和“必须 allow”.
  - 基线收敛后再将 `--check` 接入 `just qa`.

## Risks / Trade-offs

- 若直接在当前基线上启用硬门禁,会让 `just qa` 立刻失败且噪声较大.
- 文件级 allow 虽能快速收口,但会降低约束粒度;因此需要优先用于框架反射边界,不应滥用在普通业务逻辑中.
- 对部分热点模块做静态化重构时,需要同步补充类型契约或回归测试,避免“去掉 `getattr` 但收窄过度”.
