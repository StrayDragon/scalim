### Current YAML DSL inventory (high level)

顶层字段:
- `name` (required)
- `_templates` (YAML anchors/alias 复用集合;部分子键有语义)
- `description`
- `batch_size` (null-or-int)
- `retry` (全局 loader retry 默认策略)
- `main_source` (required)
- `sources`
- `fields` (仅派生字段; `compute`/`call_by`)
- `relations`
- `guardrails`
- `output`
- `observability`

核心子结构(按“读写时最常踩坑”排序):
- `main_source`: `source_id/loader/params/order_by/fields`
- `sources.<id>`: `loader/key/params/fields/lookup_cast/lookup_chunk_size/cache_mode/normalize/retry`
- `relations.<id>.steps[*]`: `from/to/(lookup_cast)` (支持单字段与同源字段列表)
- `source fields`: `name/extract/relation/value_cast/(source?)` (extract 是 current-row-relative 路径表达式)
- `derived fields`: `name/(compute|call_by)` (依赖自动推导;禁止 `depends_on`)
- `output`: `format/path/streaming/include_header/header_fields_output_by/fields[...]`(字段选择/覆写)

完整字段清单与 hover 文案请直接以 `syntax-catalog.gen.md` 为准,本 change 不复制全量 catalog,只抽取用于“重构提案”所需的结构与痛点。

### Where complexity comes from (root causes, with code pointers)

1) **“同一概念多入口”导致用户心智割裂**
- 源字段只能在 `main_source.fields` / `sources.*.fields` 声明,派生字段只能在顶层 `fields`。
- relation 定义在 `relations` 里,但字段里又允许内联 steps(或 alias)。
- `params` 同时承载 `$runtime.*` 占位符与 `$keys/$rows` 指令节点,并且对 main/source/cache_mode 有差异化约束(见 `ValidatorSourcesMixin._validate_params_template_semantics`)。

2) **输出字段选择依赖 YAML alias “对象身份”**
- `output.fields` 的解析依赖 `AliasIndex(id(obj))` 与 `OutputFieldResolver` 的多路径解析(见 `src/scalim/dsl/by_yaml/config_parsing/models/__init__.py`、`field_index.py`、`validator_fields_output.py`)。
- YAML merge(`<<`) 会生成新对象,导致 alias 身份丢失,因此又引入了“显式选择器(field_id/field/source)”这一套规则。

3) **relation 引用不支持字符串 ref**
- 字段的 `relation` 只允许 steps 对象或 YAML alias,不允许 `relation: <relation_id>` 字符串(见 schema 与 `ValidatorRelationsMixin`)。
- 这迫使用户要么写冗长 steps,要么学习 anchors/alias 的“定义在前”约束。

4) **field_id vs data_key 的双重命名体系**
- relation steps 必须写 field_id(不是 loader data_key),同时 source fields 又允许 `extract` rename/nested path。
- 于是 validator 需要做更多“避免误用 data_key”的诊断(见 `ValidatorRelationsMixin._validate_step_field_names`)。

5) **schema + 语义 validator 双层约束不可避免,但缺少“单一可解释语言”**
- schema 负责结构与 hover,validator 负责语义(unknown fields、chain、ambiguity、safe compute/call_by 等)。
- 当前语法的特殊规则越多,越需要在 docs/skill 中解释,维护成本线性上升。

## Goals / Non-Goals

**Goals:**
- **直觉化**: 新用户读一遍 canonical example 就能写出可用配置,不用先理解 YAML alias 对象身份。
- **统一化**: 每个概念尽量只有一个入口;如果必须多入口(例如内联 vs 复用),必须有统一的 ref 语义。
- **可校验/可生成**: 仍然以 JSON Schema + 语义 validator 为两层事实来源,并可用于 editor/agent。
- **一步到位**: 不引入版本标签;旧写法不保留兼容分支;仓内所有 YAML 示例/fixtures/skill/frontend 一次迁移。
- **可实现**: 至少包含一套“低风险可落地”的方案(即便其它方案更激进)。

**Non-Goals:**
- 本 change 不实现任何 runtime 逻辑,只做提案与对比。
- 不在此阶段修改 `openspec/specs/*` 的既有 requirements(选定方案并进入实现时再做)。

## Decisions

### Decision 1: 先固化“语言设计准则”(校准目标),再对比 5+ 语法方案

不先拍脑袋定语法,而先统一校准目标(“什么算直觉化/统一化/可维护”),再输出 5+ 候选方案与 MVP 示例,确保 review 能基于同一评估维度讨论。

统一校准准则(适用于所有候选方案):

1) **No required anchors**: YAML anchors/alias 可以作为“可选复用”,但 MUST NOT 成为语义正确性的必要条件。
2) **Explicit references**: 引用其它对象时优先 `ref:`/`id:`/`source:` 这类显式引用,避免依赖对象身份。
3) **One place per concept**: main/source/field/relation/output/policy 各自只有一个“主要入口”;次入口只能是 sugar。
4) **Stable names**: 避免同义词漂移(如 `source_id` vs `source` vs `id`);命名要全局一致。
5) **Editor-first**: 任何语法糖都必须能被 JSON Schema 表达或被 validator 给出可理解诊断。

### Decision 2: 方案输出结构固定在 `mvp/plan-*`

每套方案在 `openspec/notplan-changes/yaml-dsl-syntax-overhaul/mvp/plan-*/` 中包含:

- `plan.md`: 语法结构、关键规则、与当前 DSL 的映射、优缺点与实施成本
- `mvp.yaml`: 完整可读的 MVP 示例(覆盖 main + 至少一个 join + 至少一个 derived + output + params)

这让 review 可以直接 diff 对比 “同一个业务配置在不同语法下长什么样”。

### Decision 3: 同时提供“微调清单”(不依赖重构也能减痛)

即使最终选择了激进方案,也需要一组可单独落地的 micro-tunes 用于:
- 先减少 footgun(提升当前语法可用性)
- 作为迁移期的过渡手段(先改善写法,再换语法)

微调清单见 `mvp/current/micro-tunes.md`。

## Candidate Plans (summary)

本 change 提供 6 套候选方案,其中至少一套为“可落地方案”(plan-e):

- **Plan A (推荐)**: “sources 统一入口 + 显式 refs + select 输出”——尽量保留 YAML 映射的可读性,但移除对 alias 身份的依赖。
- **Plan B**: “SQL-ish from/join/select”——把报告配置变成结构化查询,对数据/SQL 用户最直觉。
- **Plan C**: “pipeline steps DAG”——显式 DAG 步骤与产物,适合复杂编排与可视化,代价是写法更长。
- **Plan D**: “type-tagged arrays”——把所有对象都变成带 `id` 的数组项,合并/patch/生成更稳定,但不如映射直观。
- **Plan E (可落地/微调优先)**: 基于当前 DSL 的最小破坏式重整: 引入字符串 ref、简化 output.fields、统一命名,以最低实现成本显著降复杂度。
- **Plan F**: “template + run”——把 DSL 拆成“可复用模板(静态)”与“运行覆写(动态)”,让 params/overrides 更直觉。

## Risks / Trade-offs

- [过度追求简化导致丢表达力] → 所有方案都以“现有能力完整映射”为硬约束;语法仅改变表达方式。
- [方案太多导致 review 发散] → 在 spec 中给出决策矩阵与 must-have 列表;强制最终只选一个 canonical plan。
- [editor/schema 跟不上语法糖] → 校准准则要求 schema/validator 能解释所有语法糖,否则不纳入 MVP 范围。
- [一步到位迁移成本过高] → Plan E 提供可落地最小方案;其余方案可作为长期方向或分阶段落地。

## Migration Plan (proposal-level)

实现阶段(不在本 change 内)建议按以下“一步到位但可控”的迁移策略推进:

1) 选定一个 plan,把它变成唯一 canonical YAML DSL 语法
2) 编写升级器(脚本/CLI 子命令),把仓内所有 YAML 一次性迁移
3) 更新:
   - canonical demo: `notebooks/marimo/demo_big_data_report/by_yaml_dsl/ecommerce_report.yaml`
   - schema 生成物与 editor schema
   - skill references 与 docs guide
4) `just gen` + `just qa` + `just openspec-check` 作为门禁
