## Context

scalim 当前存在大量分散的错误/异常类型与抛错风格:
- 一部分路径直接抛 `ValueError`/`TypeError`/`RuntimeError` 等内置异常,消息格式与信息密度不一致。
- 一部分模块定义了局部的自定义异常(例如 workflow/guardrails/dsl parsing),但缺少统一的“错误分类 / 错误码 / context/hint”契约。
- 规范层面虽然对“错误信息必须可诊断/不得泄露敏感信息”等有零散约束,但缺少统一的可复用标准,导致错误口径与测试断言容易漂移。

本变更目标是先把“错误体系”规范化为一个可测试、可渐进迁移的 SSOT,再按任务逐步落地到各模块。

## Goals / Non-Goals

**Goals:**
- 定义 scalim 的错误分类与异常类型体系(用户输入/配置错误、运行期护栏违规、系统内部错误、第三方依赖错误等)。
- 引入稳定错误码约定(字符串码,可用于测试断言与用户诊断),并规定错误 message 的结构与敏感信息治理原则(默认不泄露)。
- 明确“用户可感知错误”的最小字段集与可选字段(context/hint),并允许不同入口(库/API/CLI)以一致方式呈现。
- 给出可执行的迁移路径与验收口径(哪些错误点必须迁移、如何逐步替换既有异常、如何更新测试断言)。

**Non-Goals:**
- 不在本 change 中完成全仓库错误点的全面重构(本 change 产出规范/任务,实现按后续任务逐步推进)。
- 不强制一次性替换所有内置异常为自定义异常(允许阶段性并存,但新增/改动路径优先使用新体系)。
- 不改变既有业务行为(除错误呈现更清晰/更一致外),也不引入新的外部依赖。

## Decisions

### 1) 错误码采用稳定字符串,而非 Enum 作为公开契约
**Decision:** 以稳定字符串错误码作为跨模块契约,并规定命名规则(例如 kebab-case/分层前缀).实现可用常量集中管理,但对外契约是字符串本身。

**Why:** 字符串更易跨版本/跨语言消费(包括 CLI 输出与日志/事件),也更利于测试断言与文档引用;避免 Enum 带来的导入/序列化/兼容性复杂度。

**Alternatives considered:**
- 使用 Enum 统一管理:可读性高但会引入序列化与兼容性负担,且对外输出仍需转字符串。
- 完全不引入错误码:继续依赖 message 匹配会导致测试脆弱与文档难以稳定引用。

### 2) “用户可感知错误”优先通过基类 + 最小字段集规范化
**Decision:** 引入一个面向用户的异常基类(概念名 `ScalimError`,实际命名按实现阶段确认),并规定最小字段集:
- `code`: 稳定错误码(必填)
- `message`: 人类可读的主消息(必填,不得泄露敏感信息)
- `context`: 可选结构化信息(默认仅包含安全字段;必要时做 redaction)
- `hint`: 可选迁移/修复建议(面向用户)

**Why:** 这能让库/API/CLI 的错误呈现统一,同时让测试可以断言 `code` 与关键字段,而不是 fragile 的整段 message。

### 3) 迁移策略采用“新增优先 + 关键路径优先”的渐进方式
**Decision:** 迁移分阶段推进:
1) 新增/重构代码路径必须使用新错误体系(以减少新增债务)。
2) 关键入口与高频报错路径优先迁移(例如 YAML config 校验、execution 参数校验、guardrails fail-fast)。
3) 存量分散错误按模块逐步迁移,并允许在过渡期保留内置异常,但需要补充稳定的迁移提示与测试口径。

**Why:** 全量一次性替换风险过高;渐进迁移可控且可持续。

## Risks / Trade-offs

- [迁移成本与局部不一致] 过渡期会并存多种异常类型 → 缓解:明确“新增必须用新体系”,并提供优先级迁移清单与验收门禁(例如关键模块必须迁移)。
- [信息泄露风险] 更结构化的 context 可能携带敏感数据 → 缓解:规范层强制默认 redaction,并要求错误 message/context 均遵循“不泄露敏感值”的原则。
- [测试断言调整] 现有测试可能依赖 message → 缓解:提供推荐断言策略(优先断言 `code`,其次断言少量稳定子串),并在迁移任务中逐步替换。

## Migration Plan

- 规范 SSOT: `openspec/specs/error-taxonomy/spec.md`(本 change 新增)。
- 文档治理边界:
  - 不直接编辑任何包含 `.gen.` 的文件。
  - 不编辑任何 `<!-- BEGIN AUTOGEN:<id> -->` / `<!-- END AUTOGEN:<id> -->` 注入区块内部。
  - 若需要对外文档化,优先在 OpenSpec specs 完成,并用 `just gen-docs` 同步生成页/注入区块(由 `just qa`/CI drift gate 兜底)。
